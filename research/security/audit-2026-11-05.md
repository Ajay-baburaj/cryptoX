# CryptoX security review — 5 November 2026

Scope: application source, Firebase Authentication configuration, deployed Python inventory, project firewall/IAM configuration, VM service isolation/file permissions, and low-volume public HTTPS/header checks. This is a targeted review, not a penetration-test certification. No password guessing, load testing, or real notification sends were performed.

## Verified safeguards

- Separate CryptoX project, VPC and VM; Nifty infrastructure unchanged.
- CryptoX VPC exposes 80/443 publicly. SSH is limited to Google's IAP source range. Python port 8000 and Caddy administration port bind to loopback.
- Default-network SSH/RDP rules exist in the project, but do NOT apply to the CryptoX VM's custom VPC. Review/remove unused default infrastructure separately.
- Application runs as unprivileged `cryptox`, with NoNewPrivileges, strict filesystem protection, writable state directories and memory limit.
- `.env` and cookie-signing secret are mode 0600, owned by cryptox.
- TLS, HSTS, anti-framing and MIME-sniffing protection are present on public endpoints.
- Private API rejects unauthenticated requests with 401; Firebase signature/audience/time checks plus issuer/subject checks and an email allowlist protect access.
- VM uses a dedicated FCM service account rather than a downloaded private key. It is not the default service account with Editor privileges.
- The apt upgrade timer is enabled. This alone does not verify every OS patch has been installed or that unattended-upgrades policy is complete.

## Remediation in this review

1. Disabled Firebase public account registration through `client.permissions.disabledUserSignup=true`, and read back the setting successfully. Existing manually created users remain intact.
2. Identified old pip 23.0.1 and setuptools 66.1.1 with published PyPI advisories. Upgrade and dependency-consistency verification are recorded in the completion note below. Updated the VM installer to require fixed versions on future deployments.

The pre-remediation Python advisory results are in `python-advisories-before.json`. 57 third-party packages were queried against their exact-version PyPI advisory metadata; 55 returned no advisories and two build tools returned advisories. This does not cover Debian packages, the Firebase browser SDK, or vendored JavaScript and does not establish exploitability of each advisory.

## Remaining work, in priority order

### High priority: authentication abuse and availability

The bearer-authentication path has no rate limit, while token verification can fetch Google's certificates on each request. Implement bounded per-client/global limits, certificate caching with timeouts, and a cap on concurrent verification work. Rate-limit push test/registration mutations as well. The existing cookie-login limiter uses request.remote; behind Caddy this identifies the proxy, so one client could exhaust the shared login limit. Resolve client addresses only from an explicitly trusted proxy with overwritten forwarding headers. CORS does not prevent direct HTTP abuse. A single VM remains vulnerable to volumetric denial of service; application throttling alone is not DDoS protection.

### High priority: administrator MFA and recovery

Firebase project's MFA state is DISABLED and no custom password policy is configured. Implement and test a second-factor sign-in flow (prefer TOTP) and enroll the administrator before enforcing it. Confirm recovery access and a strong unique password; the review cannot assess the existing password. Also enable MFA on the Google Cloud owner account; its MFA status was not inspected.

### Medium priority: session invalidation

Backend verification does not check whether a Firebase user was disabled or tokens revoked after issuance. Hosted ID tokens can remain usable until expiration. Local signed cookies last up to 12 hours and logout only clears the browser cookie, so a copied cookie remains valid until expiry. Add revocation/disabled-user checks and server-side session invalidation, and cap exchanged-cookie expiry to the remaining ID-token lifetime. Consider pinning administrator Firebase UIDs in addition to email addresses.

### Medium priority: browser injection protection

Neither public endpoint sets Content-Security-Policy. Introduce a tested policy restricting scripts, connections, workers, frames, objects, base URLs and forms to the app's actual Firebase/Binance/API dependencies. Avoid allowing arbitrary inline scripts. Several strategy-rendering paths interpolate strings into innerHTML; the current values come from the strategy rather than a public text-input endpoint, but escape them or use textContent to prevent future stored-XSS regressions. Validate notification click URLs as same-origin.

### Medium priority: persistence, updates and monitoring

Configure off-VM backups with a restore test, security/availability alerts, and periodic dependency/advisory scans. The retained disk is not a backup. Review Debian security patch status and unattended-upgrade configuration. Pin/review deployment dependencies; isolate the production runtime from unnecessary research/build packages where practical.

### IAM hygiene

The unused default Compute service account has Editor in the project; it is not attached to the CryptoX VM. Check for other usage before removing that grant. Review owner/admin account access and service-account keys periodically. The CryptoX VM's FCM role is narrower than Editor but still warrants monitoring for notification abuse.
